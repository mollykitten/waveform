# Flutter / Dart AI rules

Урезанная выжимка из официальных правил Flutter
(<https://github.com/flutter/agent-plugins/tree/main/rules>). Выброшены разделы,
которые конфликтуют с конвенциями этого репозитория: навязанный state
management, `go_router`, темы/визуальный стиль, «объясняй новичку null safety».
Конвенции проекта в `CLAUDE.md` всегда важнее этого файла.

## Инструменты вместо команд

Dart MCP server (`plugin:dart-flutter:dart-mcp-server`) уже подключён. Предпочитай
его инструменты запуску тех же команд через shell — они возвращают структурированный
результат, который можно прочитать:

| Задача | Инструмент | Вместо |
|---|---|---|
| Статический анализ | `analyze_files` | `flutter analyze` |
| Автофиксы анализатора | `dart_fix` | `dart fix --apply` |
| Форматирование | `dart_format` | `dart format` |
| Тесты | `run_tests` | `flutter test` |
| Запуск приложения | `launch_app`, `list_devices` | `flutter run` |
| Горячая перезагрузка | `hot_reload`, `hot_restart` | клавиша `r` в консоли |
| Ошибки времени выполнения | `get_runtime_errors`, `get_app_logs` | чтение stdout |
| Дерево виджетов, выбранный виджет | `get_widget_tree`, `get_selected_widget` | DevTools глазами |
| Поиск пакета, pubspec | `pub_dev_search`, `pub` | `flutter pub add` |
| Символ → определение/сигнатура | `resolve_workspace_symbol`, `hover`, `signature_help` | grep по коду |

## Горячая перезагрузка при правке `lib/**`

После правки `.dart` под `lib/`, если приложение запущено (`list_running_apps`):

* `hot_reload` — правки UI-виджетов, тел `build()`, простых методов.
* `hot_restart` — изменения `main()`, `initState`, глобального/статического
  состояния, регистрации провайдеров, фундаментальной логики.
* Не перезагружать при правках только комментариев, пробелов, а также файлов вне
  `lib/` (`test/`, `integration_test/`, `tool/`).

## Качество кода

* Строка ≤ 80 символов. `PascalCase` — классы, `camelCase` — члены и функции,
  `snake_case` — файлы.
* Функции короткие, с одной ответственностью (ориентир — до 20 строк).
* Осмысленные имена без сокращений. Пиши прямолинейный код, а не «умный».
* Не глотай ошибки молча. Обрабатывай то, что может упасть.
* Документируй публичные API. Комментируй неочевидное, не комментируй очевидное.
* Не пиши trailing-комментарии в конце строки кода.
* Логируй через `dart:developer` `log()` (или логгер проекта), не через `print`.

## Dart

* Следуй [Effective Dart](https://dart.dev/effective-dart).
* Строгая null safety. Избегай `!`, пока значение не гарантированно не-null.
* `async`/`await` для одиночных асинхронных операций, `Stream` — для
  последовательности событий; в обоих случаях с обработкой ошибок.
* Исчерпывающие `switch`-выражения вместо цепочек `if`; pattern matching там, где
  он упрощает код; записи (records) вместо класса ради двух значений.
* `try-catch` с типами исключений по смыслу; собственные исключения для
  специфичных ситуаций.
* Стрелочный синтаксис для однострочных функций.

## Flutter

* Виджеты неизменяемы; UI меняется пересборкой дерева.
* Композиция вместо наследования. Маленькие приватные классы-виджеты вместо
  приватных методов, возвращающих `Widget`.
* Разбивай большие `build()` на мелкие переиспользуемые виджеты.
* `const`-конструкторы везде, где возможно — это режет пересборки.
* `ListView.builder` / `SliverList` для длинных списков.
* Никаких сетевых вызовов и тяжёлых вычислений внутри `build()`.
* `compute()` для дорогих вычислений (парсинг больших JSON), чтобы не блокировать
  UI-поток.

## Тесты

* Arrange–Act–Assert (Given–When–Then).
* Юнит-тесты — доменная логика и слой данных; widget-тесты — UI-компоненты;
  `integration_test` — сквозные пользовательские сценарии.
* Предпочитай fake/stub мокам. Если мок неизбежен — `mocktail`.
* Пиши код так, чтобы его можно было тестировать: внедряй зависимости через
  конструктор, чтобы подставлять in-memory реализации.

## Пакеты

* Добавляй зависимости инструментом `pub` (или `flutter pub add`), а не правкой
  `pubspec.yaml` руками — так подтянется совместимая версия.
* Перед добавлением новой зависимости проверь `pub_dev_search` и объясни, зачем
  она нужна.

* **State management — Riverpod** (`flutter_riverpod`), навигация —
  `go_router`. Не предлагай Provider/Bloc/GetX и не переизобретай навигацию

  `list_devices`/`launch_app` в расчёте на мобильное устройство.

  Отдельного шага проверки формата в CI нет — `dart_format`/PostToolUse-хук
  всё равно форматируют правки по ходу работы.
* **Авторство коммитов переопределено.** Автор и коммиттер — `alina
  <hi@alina.sh>` (см. `CLAUDE.md`). НЕ добавлять `Co-Authored-By: Claude`

* Все числа/тайм-коды/адреса кошельков — через `AppTheme.mono()` helper, не
